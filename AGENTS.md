## Project Overview

Fieldnotes (AI Security Vendor Register) is a React and TypeScript application for searching, viewing, editing, and refreshing AI security vendor records collected from [CybersecTools](https://cybersectools.com/categories/ai-security) (pages 1 and 2).

Key functionality:
- Browse and filter AI security vendors (All / Page 1 / Page 2) with debounced search across name, website, and description.
- View detailed vendor metadata and edit company details (name, website, description) with client and server-side validation.
- Refresh individual vendor records directly from their CybersecTools source tool page using resilient browser automation.
- Persist vendor records and updates in a PostgreSQL database managed via Drizzle ORM.

See `README.md` for background context and data collection notes.

---

## Technology Stack

- **Frontend**: React 19, TypeScript, Vite 7, Vanilla CSS (`src/styles.css`), Lucide React icons.
- **Backend**: Node.js (ESM), Express 5, `tsx` for TypeScript execution and watch mode.
- **Database & ORM**: PostgreSQL (e.g., Neon serverless or local Postgres) via `pg` (node-postgres), Drizzle ORM (`drizzle-orm`), and Drizzle Kit (`drizzle-kit`) for schema migrations.
- **Scraping & Automation**: Playwright (Chromium) for upstream page retrieval through edge firewall / anti-bot challenges (`server/playwrightFetch.ts`), Cheerio for deterministic DOM extraction (`server/source.ts`).
- **Validation**: Zod 4 for request payload schemas at API boundaries.
- **Testing**: Vitest 5, PGlite (`@electric-sql/pglite` & `drizzle-orm/pglite`) for fast in-memory PostgreSQL integration testing without external database dependencies.

## Setup and Commands

### Prerequisites
Node.js (>= 20) and npm. Playwright requires Chromium (`npx playwright install chromium`).

### Installation
```sh
npm ci
```

### Environment Configuration
Ensure `.env` exists in the repository root with a valid PostgreSQL connection string:
```sh
DATABASE_URL=postgresql://user:password@host/database?sslmode=require
DATABASE_SSL=true
PLAYWRIGHT_HEADLESS=true
```

### Database Seeding & Migrations
```sh
npm run db:migrate   # Run pending Drizzle schema migrations
npm run seed         # Migrate schema and scrape/seed vendors into PostgreSQL
```

### Local Development
```sh
npm run dev          # Run backend watcher (port 3001) and Vite dev server (port 5173) concurrently
```
Or run individually:
```sh
npm run dev:server   # Backend watcher: tsx watch server/index.ts
npm run dev:web      # Frontend server: vite --host 0.0.0.0
```
Frontend runs at `http://localhost:5173`; API runs at `http://localhost:3001`. Vite proxies `/api` calls to `http://localhost:3001`.

### Build & Production
```sh
npm run build        # Strict TypeScript type check (tsc -b) and Vite production bundle
npm start            # Run production Express server with compiled assets in dist/
```

### Testing
```sh
npm test             # Run all test suites with Vitest (vitest run)
```

## Database and Backend Architecture

### Data Model (`server/database/schema.ts`)
The `vendors` table stores normalized company records:
- `id` (text, PK): Normalized slug derived from company name (e.g. `airlock-digital`).
- `name` (text, NOT NULL): Company name.
- `website` (text, NOT NULL): Primary company URL.
- `description` (text, NOT NULL): Company/product summary.
- `source_url` (text, NOT NULL): CybersecTools tool page URL used as origin.
- `source_page` (integer, NOT NULL): Origin category page (1 or 2).
- `created_at` (timestamptz, default now()): Record creation timestamp.
- `updated_at` (timestamptz, default now()): Last modification timestamp.
- `refreshed_at` (timestamptz, nullable): Last successful CybersecTools refresh timestamp.

### Repository Pattern (`server/database/index.ts`)
All database operations pass through `createVendorRepository(db)` implementing `VendorRepository`:
- `listVendors(search?)`: Case-insensitive search across `name`, `website`, and `description`, sorted by name.
- `getVendor(id)`: Find vendor by ID.
- `updateVendor(id, draft)`: Update `name`, `website`, `description`, and set `updatedAt = now()`.
- `refreshVendor(id, draft)`: Update fields and set both `refreshedAt = now()` and `updatedAt = now()`.
- `insertVendorIfNotExists(vendor)` / `insertVendorsIfNotExist(items)`: Idempotent inserts (`ON CONFLICT DO NOTHING`).

### Express Server Factory (`server/index.ts`)
The Express application is decoupled via `createApp({ store, fetchPage })`:
- `store` defaults to the PostgreSQL repository, but can be replaced with an in-memory store in tests.
- `fetchPage` defaults to `playwrightFetchPage`, but can be replaced with a stubbed fetcher in tests.
- When compiled assets exist in `dist/`, Express serves static assets and falls back to `dist/index.html` for client routing (non-API paths).

### Browser Scraping & Upstream Protection (`server/playwrightFetch.ts`)
- CybersecTools is protected by Vercel Edge Firewall challenge mode. Standard HTTP `fetch()` receives 429 challenge pages.
- `playwrightFetchPage` launches headless Chromium, navigates with `domcontentloaded`, and detects security checkpoints or HTTP 429 status.
- Requests are serialized through a promise queue to prevent overwhelming upstream services or spawning excessive browser contexts.

## Architectural Patterns & Conventions

### 1. Vendor Normalization & Deduplication
- Multiple CybersecTools listings belonging to the same vendor are consolidated under a single company entry using `toVendorId` (`server/utils/vendors.ts`).
- `sourceUrl` references a representative tool page.

### 2. All-or-Nothing Refresh Safety (`refreshVendorRecord`)
- Refresh validates that `sourceUrl` uses `https:` and hostname `cybersectools.com`.
- Refreshes only update the database if the fetch succeeds **and** all three required fields (`name`, `website`, `description`) are successfully parsed.
- If upstream returns a 429, challenge, 5xx, or incomplete DOM, existing vendor values are **never modified or cleared**.
- The API returns clear HTTP status codes: 404 (not found), 400 (invalid source host), 422 (incomplete upstream data), 429 (rate limited), 502 (network/upstream failure).

### 3. Dependency Injection for Testability
- Route handlers and refresh functions do not access global singletons directly; they receive `store` and `fetchPage` dependencies.
- Production wiring is performed in `server/index.ts` only upon direct script execution.

## API Specification

All API endpoints return JSON. Errors include an `{ "error": string }` payload.

| Method | Endpoint | Description | Status Codes |
|---|---|---|---|
| `GET` | `/api/vendors?q={query}` | Search and list vendors | `200` |
| `GET` | `/api/vendors/:id` | Get vendor details by ID | `200`, `404` |
| `PUT` | `/api/vendors/:id` | Update vendor fields (`name`, `website`, `description`) | `200`, `400`, `404` |
| `POST` | `/api/vendors/:id/refresh` | Refresh vendor from CybersecTools source | `200`, `400`, `404`, `422`, `429`, `502` |

**Validation Rules (Zod schema)**:
- `name`: String, trimmed, 1–160 characters.
- `website`: String, trimmed, max 2048 characters, must be empty or start with `http://` or `https://`.
- `description`: String, trimmed, max 12000 characters.

## Frontend & UI Conventions

- **State Management**: Centralized in `useVendors` hook (`src/hooks/useVendors.ts`). Handles debounced search (300ms), category filtering, selected vendor tracking, form draft buffering, save mutation, and refresh trigger.
- **Components**: Separated by responsibility into `directory/` (lists, search, filter tabs), `detail/` (drawer, form, metadata), and `layout/` (navigation bar, page header, footer).
- **Styling**: Single CSS file `src/styles.css` using CSS custom properties for dark mode, glassmorphism card surfaces, and subtle micro-interactions. Do not install TailwindCSS or heavy UI frameworks without explicit requirements.
- **Feedback**: Persistent visual indicators for loading, saving, refreshing states, inline field errors, and success notices.

## Authentication and Authorization

There is currently **no authentication or authorization** middleware implemented. The project is designed as an evaluation and development register for local use. Do not expose this service directly to public networks without introducing authentication, CORS restrictions, and rate limiting.

## Coding Conventions & Constraints

### TypeScript & Modules
- Strict mode is enforced (`strict: true`, `noUnusedLocals: true`, `noUnusedParameters: true`).
- Server files use ECMAScript Modules (ESM). All local imports in TypeScript server files must include explicit `.js` extensions (e.g. `import * as schema from "./schema.js";`).

### Testing Rules
- Every test suite must run purely offline and isolated.
- Tests must never touch the live PostgreSQL database or make real HTTP requests to CybersecTools.
- Use `makeStore` and `respond` from `server/testUtils.ts` for unit/route tests.
- Use PGlite (`@electric-sql/pglite`) for SQL repository tests.

### Things an Agent Should NOT Change Casually
1. **Never bypass refresh validation**: Do not remove the `cybersectools.com` domain check or allow arbitrary URL scraping.
2. **Never overwrite good data on scrape errors**: Maintain the atomic all-or-nothing update check in `refreshVendorRecord`.
3. **Never connect to live databases in tests**: Keep `server/__test__/setup.ts` intact.
4. **Never perform destructive database changes without migrations**: Use `drizzle-kit` to generate and apply migrations when altering `schema.ts`.
5. **Always verify before finishing**: Run `npm test` and `npm run build` after changes.
